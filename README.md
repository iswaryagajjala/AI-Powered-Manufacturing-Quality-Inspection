# AI-Powered Manufacturing Quality Inspection System

An end-to-end computer vision system that classifies images of steel/surface
components as **defective or non-defective** (with defect sub-type), simulating
an automated visual inspection station on a manufacturing production line.

> **Status note:** This repository ships with complete, runnable code for the
> entire pipeline. The metrics quoted in this README under "Results" are
> placeholders (`TBD`) until you run training on your machine with the real
> dataset — see `RESULTS.md` (auto-generated by `train.py`/`evaluate.py`) for
> the actual numbers once you do. **No result in this repo is fabricated.**

## 1. Problem Statement

Manual visual inspection on production lines is slow, inconsistent, and
expensive to scale. This project builds a CNN-based inspection system that:

1. Takes an image of a manufactured part (e.g. a steel surface sample).
2. Classifies it into one of several defect categories (or "no defect").
3. Returns a confidence score and an automated **ACCEPT/REJECT** decision.
4. Is served behind a REST API so it can be integrated into a real inspection
   line (camera → API → PLC/robot arm decision).

## 2. Dataset Decision

Three candidate datasets were evaluated for this project:

| Dataset | Images | Classes | Task type | Fit for this project |
|---|---|---|---|---|
| **NEU Surface Defect Database (NEU-DET/NEU-CLS)** | ~1,800 (NEU-CLS) | 6 defect types | Classification (NEU-CLS) / Detection (NEU-DET) | ✅ Best fit |
| MVTec AD | ~5,000 | 15 object/texture categories, many defect sub-types | Anomaly detection (unsupervised, pixel-level) | Powerful but heavier — designed for anomaly segmentation, not simple classification; steeper implementation curve |
| Kaggle Casting Product Defect | ~7,000 | 2 classes (defective/ok) | Binary classification | Good but too simple to show multi-class skill |

**Recommendation: NEU Surface Defect Database (NEU-CLS variant).**

Reasoning:
- **Directly manufacturing-relevant**: real hot-rolled steel strip surface
  images collected from an actual production environment.
- **Multi-class, not artificially binary**: 6 real defect categories
  (`crazing`, `inclusion`, `patches`, `pitted_surface`, `rolled-in_scale`,
  `scratches`), so the project demonstrates genuine multi-class
  classification rather than a toy binary problem.
- **Right-sized for a portfolio project**: ~1,800 images (300/class) trains
  in minutes on transfer learning without needing a large GPU budget, and is
  small enough to fully explore/understand — unlike MVTec's much larger,
  segmentation-oriented format.
- **Well-documented and widely used** in academic QA/QC research, so results
  are easy to benchmark and discuss credibly in an interview.
- **Clean classification task**: label = folder name, no need to build
  pixel-level mask handling (which MVTec would require) — keeps the project
  focused on the classification pipeline you were asked to demonstrate
  (CNN, transfer learning, evaluation, API), not segmentation.

MVTec AD is noted in the README as a "Future Work" extension (anomaly
detection / unsupervised setting) since it's a natural next step but a
different, harder problem (one-class learning) than what's needed here.

**Classification type: Multi-class (6 classes).** The dataset naturally
supports 6 distinct defect categories, and collapsing them into a single
"defective" bucket would throw away real signal a manufacturing engineer
would want (different defects → different root causes / rework stations).
The API additionally derives a simple binary `inspection_status`
(ACCEPT/REJECT) from the multi-class prediction, which mirrors how a real
line would use this model.

### Getting the dataset
1. Download NEU-CLS from Kaggle: search "NEU surface defect database" (e.g.
   `kaustubhdikshit/neu-surface-defect-database` or the original
   `fantic/NEU-CLS` mirror), or the original source page at
   http://faculty.neu.edu.cn/yunhyan/NEU_surface_defect_database.html
2. Extract it so you have one folder per class:
   ```
   data/raw/NEU-CLS/
     crazing/
     inclusion/
     patches/
     pitted_surface/
     rolled-in_scale/
     scratches/
   ```
3. Run `python src/preprocessing.py` to build the split under `data/processed/`.

## 3. Architecture

```
Camera / Image Upload
        │
        ▼
 FastAPI  /predict  ──►  Preprocessing (resize, normalize)
        │
        ▼
 ResNet18 (transfer learning, fine-tuned head)
        │
        ▼
 Softmax → {class, confidence}
        │
        ▼
 Decision rule → {ACCEPT, REJECT}
        │
        ▼
 JSON response
```

**Model: ResNet18 (ImageNet-pretrained), fine-tuned.**
Why ResNet18 over EfficientNet/MobileNet here:
- Small dataset (~1,800 images) → a smaller, well-regularized backbone
  generalizes better and is far less prone to overfitting than deeper
  EfficientNet variants.
- Residual connections make it easy to fine-tune reliably without careful
  LR-warmup schedules that larger EfficientNet/MobileNetV3 architectures
  often need.
- Fast to train/infer on CPU — realistic for an edge/on-prem inspection
  deployment, and fast to iterate on for a portfolio project.
- Extremely well understood — easy to justify architecture choices in an
  interview.
- (MobileNetV3 is called out in Future Work as the natural choice if this
  needed to run on an actual edge camera/embedded device.)

```bash
python3.11 -m venv venv

pip install -r requirements.txt
```

## 6. Running the Pipeline

```bash
# 1. Split the raw dataset into train/val/test
python src/preprocessing.py

# 2. Train (transfer learning, ResNet18)
python src/train.py --epochs 15 --batch-size 32 --lr 1e-4

# 3. Evaluate on the held-out test set
python src/evaluate.py --checkpoint models/best_model.pth

# 4. Run a single-image prediction from the CLI
python src/inference.py --image path/to/sample.jpg --checkpoint models/best_model.pth

# 5. Serve the model via REST API
uvicorn api.main:app --reload --port 8000
```

## 7. API Usage

```bash
curl -X POST "http://127.0.0.1:8000/predict" \
  -F "file=@sample.jpg"
```

Response:
```json
{
  "predicted_class": "pitted_surface",
  "confidence": 0.94,
  "inspection_status": "REJECT",
  "class_probabilities": {
    "crazing": 0.01,
    "inclusion": 0.02,
    "patches": 0.01,
    "pitted_surface": 0.94,
    "rolled-in_scale": 0.01,
    "scratches": 0.01
  }
}
```

`inspection_status` is `ACCEPT` only if the predicted class is a
configured "no-defect" label; NEU-CLS has no explicit "good" class (it's a
6-defect-type dataset), so by default every predicted class maps to REJECT,
and the mapping is exposed as a config so it can be adapted to a dataset/line
that does have a "good" class.

Interactive API docs: `http://127.0.0.1:8000/docs`

## 8. Testing

```bash
pytest tests/ -v
```

`test_model.py` checks the model builds, accepts the right input shape, and
outputs the right number of classes. `test_api.py` uses FastAPI's TestClient
to hit `/predict` and `/health` without needing a live server.

## 9. Evaluation Methodology

`evaluate.py` reports, from the actual held-out test split:
- Overall accuracy
- Per-class precision, recall, F1 (via `sklearn.metrics.classification_report`)
- Full confusion matrix (saved as `models/confusion_matrix.png`)

**Why precision/recall matter more than accuracy here:** in quality
inspection, a **false negative** (defective part predicted as fine) means a
defective unit ships to a customer — costly and potentially unsafe. A
**false positive** (good part flagged as defective) only costs a wasted
manual re-check. This means **recall on defect classes is prioritized over
raw accuracy**, and the `evaluate.py` script reports per-class recall
prominently for this reason, since a model that's 95% accurate but misses
one dangerous defect type is worse than one that's 92% accurate with high
recall on every class.

## 10. Future Improvements
- Extend to MVTec AD for unsupervised anomaly detection (handles novel,
  previously-unseen defect types instead of only the 6 trained classes).
- Swap ResNet18 → MobileNetV3 and export to ONNX/TensorRT for real edge
  deployment on a production-line camera.
- Add Grad-CAM visualization so a human inspector can see *why* the model
  flagged a part.
- Add active-learning loop: low-confidence predictions get routed to human
  review and fed back into retraining data.
- Model versioning + A/B rollout via the API (`/predict?model_version=`).
